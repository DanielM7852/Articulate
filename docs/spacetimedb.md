# SpacetimeDB

Checked against SpacetimeDB CLI and server 2.13.0 (`spacetimedb-lib` 2.13.0) and the `spacetimedb` npm package 2.13.0. The module is TypeScript. Tables are private. Clients subscribe to views. There is no Python SDK in the 2.13 client list, so the worker uses `POST /v1/database/{name}/call/{reducer}` with a JSON array of arguments.

The local development database used for the saved worker token is `articulate-dev`. An earlier local database named `articulate-local` was also published and was not deleted. This is not a Maincloud deployment, and it does not replace the local JSON session store.

## What is stored

Each Spacetime identity has its own profile and progress rows. `ensure_profile` writes the caller's identity only. `my_profile` and `my_progress` return that caller's rows. A learner cannot read another learner's attempts, chunks, or progress through those views.

Progress counts usable and unusable attempts, repeated `ending_direction_mismatch` findings, and the last cue. A repeated commit of the same attempt does not increment the counts. Fixture commits are stored with `provenance = synthetic_fixture` and are not counted. That count is not a clinical improvement, and it does not say a cue caused the next attempt.

Teachers create a classroom and a join code. Students join as themselves. A student cannot assign work in a classroom they do not teach. A teacher summary view returns counts, not audio and not every classmate's curve. `select_learner_trace` loads chunks only when the caller teaches a classroom that contains that learner.

Raw audio is not written to SpacetimeDB. Provisional curves are bounded JSON chunks of at most 8000 characters, deduplicated by attempt, sequence, and provenance. Deleting a chunk removes it from the live view. The commit log can still retain the old transaction. Do not describe that as physical deletion.

## Local setup

The CLI used here is `spacetimedb-cli.exe` 2.13.0. Start it from the extracted 2.13.0 archive, then publish without deleting data:

```powershell
spacetimedb-cli.exe start
spacetimedb-cli.exe publish articulate-local --server local --module-path spacetimedb --anonymous --yes
```

Do not pass `--delete-data`. If a database with this name already exists on the target server, stop and confirm it is the development database before publishing again.

Create a worker token with `POST /v1/identity`, then call `become_worker` once with that token. The first caller becomes the only identity allowed to commit verified findings. Put that token in `backend/.env`:

```text
SPACETIMEDB_URL=http://127.0.0.1:3000
SPACETIMEDB_DATABASE=articulate-local
SPACETIMEDB_TOKEN=<worker token>
```

Restart uvicorn after changing `.env`. Leave the token blank to skip Spacetime writes. The comparison response still returns. A failed commit adds `spacetimedb_commit_failed` and does not hide the measurements.

`backend/scripts/spacetime_local_check.py` creates fresh identities, checks that one learner cannot write another learner's chunk or a teacher's assignment, commits one verified result, repeats the commit, and prints local reducer latencies. It does not call Claude.

## Frontend and Cartesia

`web/src/spacetime/module_bindings/` is generated by:

```powershell
spacetimedb-cli.exe generate --lang typescript --out-dir web/src/spacetime/module_bindings --module-path spacetimedb
```

`web/src/spacetime/graphAdapter.example.ts` shows the subscription list and the rule for ignoring a device's own provisional echo. It is not mounted in the practice screen. The screen keeps drawing the local microphone preview without waiting for Spacetime, Claude, or alignment.

Provisional batches can also be posted to `POST /v1/feature-batches` with header `X-Spacetime-Token`. The comparison upload accepts the same header so the verified row stays owned by that learner. Without the header, the worker will not invent an owner.

After feedback is committed, `feedback.delivery_id` is stable for that attempt, status, and finding. `POST /v1/feedback/{delivery_id}/spoken` records one delivery. Calling it again does not create a second spoken event.

## Maincloud

Do this only for a new development database name. Do not republish over a database whose purpose you have not confirmed, and do not clear its data.

1. `spacetimedb-cli.exe login`
2. `spacetimedb-cli.exe publish <new-dev-name> --server maincloud --module-path spacetimedb --yes`
3. Confirm the command says the database was created, not that existing data was destroyed.
4. Create a worker identity and call `become_worker` before sharing the database name.
5. Set `SPACETIMEDB_URL=https://maincloud.spacetimedb.com` and `SPACETIMEDB_DATABASE` to that new name.

One database is not an unlimited classroom partition. If measurements later show one database is too large, give each class or organization its own database. This module does not do that split.

## Targets and what was measured

These are targets, not guarantees:

- Local provisional chunk reducer: p50 under 50 ms.
- Local verified commit: p50 under 100 ms.
- Capture-to-pixels stays on the browser and is not a database round trip.

Cross-device numbers are not one-way latency. The check script times the HTTP call on one machine with a monotonic clock. It does not subtract clocks from two devices.

The load check is a small authenticated run of chunk writes. It is not a live Claude or Cartesia benchmark.

On 2026-10-24, `scripts/spacetime_local_check.py` against local `articulate-dev` on this machine recorded:

- Verified commit: 15.8 ms for one call.
- Feature-chunk HTTP calls, n=20, same machine: p50 17.5 ms, p95 32.2 ms.
- A repeated verified commit left `usable_attempts` at 1.
- A second learner's `my_progress` query returned no rows for the first learner's exercise.
- Learner writes to another learner's chunk, a learner calling `commit_verified`, and a student assigning a class they do not teach all returned HTTP 530.

Those numbers are local reducer round trips. They are not capture-to-pixel time and they are not cross-device latency.

A second local run sent the labeled `rising_vs_falling` synthetic fixture through the Python comparison and then into `articulate-dev` with a fresh learner token. The commit sequence (`open_session`, `begin_attempt`, `commit_verified`) took 803 ms on that call. The result status was `failed` with finding `reference_unusable`, `fixture_mode` stayed true, and that learner's `my_progress` query returned no rows. That run is a fixture, not a microphone recording.
